# rugram — заводская сборка

**Свой сервер. Настоящий MTProto. Реальные клиенты Telegram.**

`rugram` — открытый сервер, совместимый с Telegram, и бэкенд MTProto на Go.
Это **заводская сборка**: её можно собрать и запустить с нуля, и она сразу
содержит всё, что мы делали последние дни — **кастомную галочку верификации** и
**набор подарков**. Конфигурация сброшена к заводским значениям, а данные
подгружаются автоматически при первом старте — ничего не нужно настраивать
руками.

Автор и мейнтейнер сборки: [@yvafa0975-ux](https://github.com/yvafa0975-ux).

## Что здесь главное

### ✅ Кастомная галочка верификации

Это механизм **сторонней верификации** (`core.telegram.org/api/bots/verification`),
отдельный от официального бейджа платформы. Верификатор-бот помечает цель своей
собственной иконкой-кастом-эмодзи, и клиент рисует её **перед именем** в списке
чатов, поиске, заголовках сообщений и профиле.

Что уже сделано в сборке:

- В репозиторий добавлен готовый набор стикеров `verifiermarks` (в
  `data/sticker-seed/`) с двумя документами:
  - `7800000000000000025` — галочка (Check),
  - `7800000000000000026` — «песочные часы»/Hold.
- При первом старте набор импортируется автоматически, а в каталог иконок
  (`verification_icons`) добавляются записи **Verifier Check** и **Verifier Hold**.
- Иконки используют `text_color: true`, поэтому клиент сам окрашивает контур
  (художественная часть — непрозрачная, opacity 100). **С фоном профиля** клиент
  подмешивает полупрозрачный белый `premiumFg` — галочка выглядит
  полупрозрачной; **без фона** она сплошная синяя. Это поведение клиента,
  сервер на итоговый оттенок не влияет.

Чтобы включить галочку в клиенте, остаётся два действия оператора (сервер не
может «печатать» бейджи сам — это было бы небезопасно):

1. **Назначить верификатора.** Админка → *Сторонняя верификация → Верификаторы*:
   укажите реального бота, выберите одну из готовых иконок (Check/Hold) и имя
   организации.
2. **Выдать метку.** Админка → *Сторонняя верификация → Метки* → **«Выдать
   метку»**: выберите верификатора и цель (user/bot/channel) по ID. Описание
   можно не указывать — подставится формулировка верификатора
   («Подтверждено организацией …»). У цели одновременно не более одной метки.

> Дополнительно: **выдача метки без заявки** — новая кнопка «Выдать метку» на
> вкладке «Метки» (раньше метку можно было выдать только через очередь заявок или
> прямой RPC-вызов). Роут `POST /api/actions/grant-bot-verification-mark`,
> право `botverification.manage`, всё проходит через журнал команд.

Подробное описание механизма: [`docs/bot_verification.md`](docs/bot_verification.md).

### 🎁 Подарки

В бинарник встроен классический набор подарков, и он **подгружается
автоматически** при первом старте (девять подарков):

| Подарок | Звёзд | При конвертации |
| --- | ---: | ---: |
| Teddy Bear | 15 | 13 |
| Love Heart | 15 | 13 |
| Gift Box | 25 | 21 |
| Red Rose | 25 | 21 |
| Birthday Cake | 50 | 43 |
| Champagne Bottle | 50 | 43 |
| Trophy | 100 | 85 |
| Diamond Ring | 100 | 85 |
| Gem | 100 | 85 |

### 🔧 Удобства для админа

Эти изменения также вошли в сборку:

- **Массовая выдача звёзд**: от 1 до 1 000 000 000 (раньше верхняя граница была
  ниже). Проверяется и на сервере, и в интерфейсе.
- **Продажа подарков за звёзды**: потолок цены поднят до **10 000 000** звёзд
  (минимум — 125). Клиенту значение сообщается через
  `stars_stargift_resale_amount_max`, сервер дублирует проверку.
- **Уникальные подарки**: в заголовке статуса-эмодзи теперь показывается
  серийный номер (`Title #N`), как в официальных клиентах.

## Быстрый старт

Нужны **Git** и **Docker Desktop** (Linux-контейнеры). PowerShell 5.1 или новее.

```powershell
# первый запуск: создаст deploy/docker/.env и соберёт образы
.\scripts\start-docker.ps1 -BridgeNetwork -AllowInsecureDevelopmentAuth -Build

# последующие запуски
.\scripts\start-docker.ps1
```

Скрипт сам создаёт `deploy/docker/.env` со случайными секретами, собирает и
поднимает стек. Флаг `-BridgeNetwork` обязателен для Docker Desktop на Windows:
host-сеть там не пробрасывает порты на хост-машину.

### Адреса по умолчанию

| Что | Адрес |
| --- | --- |
| MTProto (подключение клиента) | `127.0.0.1:2398` |
| Публичные ссылки (web) | `127.0.0.1:2401` |
| Админ-панель | `http://127.0.0.1:2600` |
| Код входа (dev) | `12345` |

Пароль админ-панели — `RUGRAM_ADMIN_UI_PASSWORD` в `deploy/docker/.env`.

### Если запускать вручную

```powershell
# 1. Сгенерировать конфиг (заводские значения + случайные секреты)
.\scripts\new-docker-env.ps1 -AdvertiseIP 127.0.0.1 -BridgeNetwork -AllowInsecureDevelopmentAuth

# 2. Собрать и поднять
Set-Location deploy\docker
docker compose --env-file .env -f compose.yaml -f compose.bridge-network.yaml build
docker compose --env-file .env -f compose.yaml -f compose.bridge-network.yaml up -d
```

> `deploy/docker/.env` **не коммитится** (в `.gitignore`). Каждая установка
> генерирует свои секреты.

## Что такое «заводские» настройки

- `deploy/docker/.env` сброшен: никаких реальных секретов, всё генерируется
  заново случайными значениями.
- Сид-данные лежат **в репозитории** и попадают в контейнер:
  - набор стикеров `verifiermarks` — через bind-mount
    `data/sticker-seed` (см. `deploy/docker/compose.yaml`);
  - классические подарки — встроены в бинарник (`internal/seed/giftseed/`).
- Оба сида идемпотентны и не фатальны: ошибка сида пишется в лог, но не мешает
  серверу подняться.

## Структура (что добавлено в этой сборке)

```
data/sticker-seed/                    набор стикеров verifiermarks + исходники галочки
internal/seed/giftseed/               встроенный набор классических подарков (9 шт.)
internal/seed/verifiericon/           сид каталога иконок верификации (Check / Hold)
cmd/rugram/main.go                   подключение обоих сидов при старте
```
